# 移动端设计规范站与组件接入计划

更新：2026-10-08。

## 已确认目标

移动端规范以网页呈现，参考已有桌面站 https://gjb2b.netlify.app 的浏览方式。右上角提供“桌面端 / 移动端”切换或跳转。现有移动端 Token、H5 规则和后续逐个接入的组件共同成为站点内容来源。

参考依据：本地 PC 目录的 preview/index.html、README.md 与 package.json。线上地址本次无法通过网页读取工具访问，尚未确认线上与本地版本一致。

## 阶段一：建立规范站与基础规范页

- 顶部品牌与当前端别、右上角端别切换；左侧规范分类；右侧文档与交互示例。
- 首批内容：概览、颜色、字体与数字、间距、圆角、控件尺寸、效果与渐变、H5 尺寸与适配。
- 从移动端现有源数据和编译产物生成展示，避免维护第二份数值表。
- 站点外层用于桌面阅读；移动示例放入独立 iframe，以 375×812 为基准。视口支持 320、375、450、600、960 等核验档位；预览倍率不改变 iframe 逻辑宽度。
- 组件目录只上架已有真实内容的条目；未接入组件的进度集中展示，不创建空规范页。
- 验收：导航、链接、Token 来源、移动预览缩放与宽度切换有效，桌面端样式不会进入移动预览。

## 阶段二：端别切换与发布接入

建议先采用两个独立站点互相跳转：桌面端继续使用现有地址，移动端站点地址待部署时确定。双方右上角使用一致的端别切换控件，清楚标出当前端别。

- 每次切换默认进入目标端首页；两端均有同类页面时可建立显式映射，例如“颜色 → 颜色”“按钮 → 按钮”。目标尚未接入时进入目标首页，不跳空链接。
- 若后续要求同域名，可采用 /mobile/ 前缀；实施前需核对现有发布目录、绝对资源路径及路由重写。本地 PC 外壳存在 /preview/ 的 base 路径，不能直接复制到 /mobile/ 下。
- 正式接入前核实 Netlify 项目与发布来源。先完成可审阅预览，再按实际发布范围执行部署；本计划不修改现有线上站点。

## 阶段三：逐个组件接入

“上传组件”在本计划中指：从用户提供的移动端 Figma 节点只读提取，在本地形成可追溯资料与网页示例，再接入规范站。若另指上传到 Figma 或真实代码组件库，另行明确目标。

每个组件完成一轮：

1. 获取指定 Figma 节点、变体、状态、文字、图标及 Token 绑定。
2. 保存原始证据，记录组件规则、适用场景与缺失信息；不推测真实前端 API。
3. 制作使用移动端 Token 的独立预览，保留真实存在的状态及可验证交互。
4. 在 375 基准和 320 小屏核验，再按组件类型检查宽屏、长文案、输入及滚动。
5. 输出核对结果，区分“已提取 / 待确认 / 预览已验证 / 已发布”。状态分开记录，不把待确认项当作已通过。
6. 加入导航与按需读取入口；后续修改只更新相关组件并重验。

建议顺序（可随实际提供的组件调整）：

- 第一批：按钮、标签、输入框、搜索框、分割线。先跑通一套组件接入流程。
- 第二批：导航栏、Tabs、底部导航、列表、卡片。
- 第三批：选择器、单选、多选、开关、表单。
- 第四批：弹窗、提示、加载、空状态及其余业务组件。

组件名称只是工作排序，不表示已经取得对应规范或确认其行为。

## 阶段四：持续维护

每次源数据更新：重新编译 Token → 校验引用 → 更新受影响的示例 → 浏览器核验 → 更新来源与发布记录。网页面向人工浏览，SKILL 及 references 面向 Agent 按需读取，使用同一组已确认资料。

## 后续实施时需要的信息

- 移动站的正式域名或 Netlify 项目（可在本地站点完成后确定）。
- 桌面站当前发布来源与可更新位置，用于加入反向跳转。
- 第一批组件的 Figma 节点链接；建议从按钮开始。

下一步：先制作本地规范站外壳与基础规范页，再以按钮作为首个组件完成接入和验收。
